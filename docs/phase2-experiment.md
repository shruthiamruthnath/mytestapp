# Phase 2 Experiment: Query Understanding + Filter-Aware Hybrid Search

## Question
Does adding natural-language constraint extraction and structured commerce filtering improve product-search relevance for constraint-rich queries compared with lexical-only and semantic-only retrieval?

## Systems

| System | Description |
|---|---|
| BM25 | lexical control |
| FAISS semantic | dense semantic retrieval with SentenceTransformers |
| Hybrid + filters | BM25 + FAISS + Reciprocal Rank Fusion + parsed commerce constraints |
| Hybrid + filters + reranker | same pipeline followed by a cross-encoder reranker |

## Dataset
The Phase 2 catalog is synthetic and intentionally small. Products include title, category, description, attributes, brand, price, rating, availability and gender. This keeps the experiment reproducible and avoids unsupported claims about proprietary retailer data.

The Phase 2 relevance set contains constraint-rich queries such as:

- `waterproof women's hiking shoes under $100 with good ratings`
- `women's hiking boots under $100 rated 4.5 stars or better`
- `65 watt usb c charger under $50 rated 4.5 stars`
- `carry on backpack with laptop space under $100`

Relevance is graded from 0 to 3.

## Query-understanding hypothesis
The parser separates free-text semantic intent from hard commerce constraints. For example:

`waterproof women's hiking shoes under $100 rated 4.5 stars in stock`

becomes approximately:

```text
semantic query: waterproof women's hiking shoes
category: Shoes
gender: women
max_price: 100
min_rating: 4.5
in_stock_only: true
```

The structured values are used as deterministic filters after hybrid candidate generation.

## Metrics

### Primary
**NDCG@10** — rewards highly relevant products near the top and supports graded relevance.

### Secondary
- Recall@10
- MRR
- average query latency in the MVP benchmark

A production evaluation should additionally use p50/p95 latency, a much larger query set, and online behavioral metrics.

## Slices
- constraint-rich
- conversational-filtered
- attribute-filtered
- exact-filtered
- semantic-filtered

Slice-level analysis matters because a system can improve aggregate relevance while regressing exact or highly structured queries.

## Decision rule
The hybrid system is a launch candidate only if it improves relevance on the intended semantic/constraint-rich slices while preserving exact-query quality and an acceptable latency budget.

The reranker should be adopted only if its incremental relevance gain justifies its added serving latency and compute cost.

## Results policy
No percentage improvement is written into the case study before the benchmark completes. The final `X%` will be computed from measured results generated by `src/phase2_benchmark.py` in GitHub Actions.

For an overall NDCG comparison, the improvement will be calculated as:

```text
((treatment_ndcg - baseline_ndcg) / baseline_ndcg) * 100
```

The case study will show both the absolute metric values and the relative improvement so the result is not misleading.
